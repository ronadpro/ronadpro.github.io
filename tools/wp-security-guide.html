WordPress Hardening

CORE CONFIGURATION
01Disable WordPress File EditorPrevent PHP editing from wp-admin

Why?

The dashboard file editor can let an administrator modify plugin and theme PHP files. Removing it reduces the impact of a compromised administrator account.

Implementation

Add to wp-config.php before the “That's all, stop editing!” line:

define( 'DISALLOW_FILE_EDIT', true );

Verify

Log in and check the plugin/theme editor. It should no longer be available.

Note: This does not stop changes through SSH, FTP, hosting panels or deployment systems.
Official WordPress Hardening Guide →
02Disable XML-RPC When Not RequiredReview integrations first

What is it?

XML-RPC lets remote applications communicate with WordPress. Some integrations can require it, so don't blindly disable it on every site.

PHP implementation

add_filter( 'xmlrpc_enabled', '__return_false' );
Important: WordPress documents that this filter disables authenticated XML-RPC methods, not necessarily every XML-RPC function. Test Jetpack and other integrations first.

Verify

Review your intended behavior at /xmlrpc.php and test site integrations.

WordPress XML-RPC Hook →
03Reduce User EnumerationLimit unnecessary username exposure

Why?

Exposed usernames can make targeted credential attacks easier. This is defense-in-depth, not a replacement for MFA.

Simple author-archive mitigation

add_action( 'template_redirect', function () {
    if ( is_author() ) {
        wp_safe_redirect( home_url(), 301 );
        exit;
    }
} );

REST API

Don't disable the entire REST API just to hide users. Review whether your site unnecessarily exposes user information and apply a narrower control where appropriate.

Verify

Test author archives and review /wp-json/wp/v2/users according to the site's privacy requirements.

04Reset WordPress Salt KeysRotate authentication secrets

Why?

WordPress secret keys and salts strengthen authentication cookies and related security mechanisms. Keep them unique and secret.

Official generator

Generate a fresh set using WordPress:

WP-CLI

wp config shuffle-salts
Plan the change: rotating salts invalidates existing authentication cookies, so users will generally need to log in again.

Core, Plugins & Updates

PATCH MANAGEMENT
05Keep WordPress, Plugins & Themes UpdatedThe most important baseline control

Why this matters

Security fixes are published through WordPress core, plugin and theme updates. An outdated component can leave a known weakness exposed even when the rest of the site is hardened.

Developer workflow

  1. Keep a staging site that mirrors production.
  2. Back up before significant updates.
  3. Review the update changelog and security advisories.
  4. Update WordPress core, plugins and themes.
  5. Test login, forms, checkout, APIs, cron jobs and important frontend pages.
  6. Deploy to production and verify again.
Good rule: don't leave a vulnerable plugin installed just because it is inactive. Remove software you no longer need.
Official WordPress Hardening Guide →WordPress Security News →
06Remove Unused Plugins & ThemesReduce the attack surface

What to do

Audit installed plugins and themes. If a component is not required, remove it instead of simply leaving it inactive.

Before removal

  • Confirm it is not required by a must-use plugin or custom code.
  • Check whether a theme is used as a parent or fallback theme.
  • Back up before making changes.
  • Test the site after removal.
Do not delete blindly: some plugins create database tables, scheduled jobs, uploads or configuration that may need a documented migration or cleanup.
07Choose Maintained Plugins & ThemesSecurity is also a vendor-selection problem

Review before installing

  • Is the plugin actively maintained?
  • Does it have a recent release?
  • Does it support your current WordPress version?
  • Does the developer respond to security issues?
  • Is the plugin actually necessary?

Prefer established sources such as the official WordPress.org directory or a vendor you trust. Avoid downloading “nulled” or pirated plugins and themes.

Server & WordPress Configuration

ENVIRONMENT HARDENING
08Protect wp-config.phpKeep database credentials and secrets private

What is sensitive?

wp-config.php can contain database credentials, authentication keys, salts and other site-specific configuration.

Recommended practices

  • Use file permissions appropriate for your hosting environment.
  • Do not commit wp-config.php or production secrets to Git.
  • Use environment variables or secret-management facilities when your deployment platform supports them.
  • Use HTTPS for administrative access.
# Example .gitignore entry
wp-config.php
.env
.env.*
Don't paste secrets into support tickets, GitHub issues or public logs. Treat database passwords, salts, API tokens and application passwords as credentials.
WordPress Hardening Documentation →
09Disable Debugging on ProductionPrevent sensitive errors from leaking

Production configuration

WordPress debugging is useful during development, but verbose errors can expose paths, SQL details, plugin names and other implementation information.

define( 'WP_DEBUG', false );
define( 'WP_DEBUG_DISPLAY', false );
@ini_set( 'display_errors', 0 );

Better workflow

Enable detailed logging only when troubleshooting, preferably in a staging or controlled environment. If production logging is necessary, keep logs protected and avoid exposing them publicly.

10Use HTTPS EverywhereProtect credentials and authenticated traffic

Minimum baseline

  • Install a valid TLS certificate.
  • Redirect HTTP traffic to HTTPS.
  • Ensure WordPress Address and Site Address use HTTPS.
  • Check mixed content.
  • Protect administrator and API traffic with TLS.
Important: HTTPS is required for safely using WordPress Application Passwords over the network.
WordPress Application Passwords Documentation →
11File Permissions & SFTPLimit unnecessary write access

Principle

Files should not be writable by more processes or users than necessary. Exact permissions depend on the hosting model.

# Common starting point — review for your host first
find /path/to/wordpress/ -type d -exec chmod 755 {} \;
find /path/to/wordpress/ -type f -exec chmod 644 {} \;
Do not run this blindly on every server. Ownership, PHP-FPM configuration, shared hosting and deployment tooling can change the correct permissions. Prefer SFTP over unencrypted FTP.
Official File Permissions Guidance →
12Database & Secrets HygieneReduce credential exposure
  • Use a dedicated database account for the WordPress installation rather than a superuser where practical.
  • Use a strong unique database password.
  • Keep database servers inaccessible from the public internet when the architecture allows it.
  • Never hard-code API keys into public JavaScript when the secret must remain secret.
  • Rotate credentials after suspected exposure.

Logging, Monitoring & Alerts

DETECT CHANGES
13Security AlertsKnow when something changes

Useful alerts

  • Administrator login or new administrator creation
  • Plugin/theme installation or update
  • Unexpected core/plugin file changes
  • Repeated failed logins
  • Malware or vulnerability findings
  • Certificate or domain problems
  • Backup failures

Configure alerting so important events reach an address or channel that is actually monitored. Avoid creating so much noise that real alerts are ignored.

Wordfence Security →
14Audit Administrator AccountsLeast privilege and account hygiene

Monthly review

  1. List all users with administrator privileges.
  2. Remove accounts that are no longer needed.
  3. Downgrade users who do not need administrator privileges.
  4. Confirm MFA is enabled for privileged accounts.
  5. Check for unfamiliar accounts or unexpected email addresses.
Least privilege: give users only the role and capabilities required for their work.
15WordPress Application PasswordsUse separate credentials for integrations

When to use them

Application Passwords provide revocable, per-application credentials for programmatic access. They avoid sharing a user's normal login password with an integration.

Good practice

  • Create one credential per integration.
  • Use HTTPS.
  • Revoke credentials that are no longer needed.
  • Rotate after a suspected leak.
  • Never put an Application Password in public source control.
curl --user "USERNAME:APPLICATION_PASSWORD" \
  https://example.com/wp-json/wp/v2/users/me

Incident Response

WHEN SOMETHING GOES WRONG
16Suspected WordPress CompromiseA practical first-response workflow

First response

  1. Do not immediately delete suspicious evidence if you may need to investigate it.
  2. Record what was observed, when it was observed and who discovered it.
  3. Preserve relevant logs and alerts.
  4. Restrict access if necessary while avoiding unnecessary destruction of evidence.
  5. Change compromised credentials from a trusted environment.
  6. Rotate exposed WordPress salts, database credentials and application/API secrets as appropriate.
  7. Identify the initial entry point — vulnerable plugin, stolen credential, hosting compromise, malicious upload or another cause.
  8. Restore from a known-good backup only after understanding whether the backup may also be compromised.
  9. Update or remove the vulnerable component.
  10. Re-scan and monitor after recovery.
Important: if the server itself may be compromised, a plugin scan alone is not enough. Consider a full host-level investigation and rebuild from trusted sources.
17After a CleanupClose the original security gap
  • Reinstall WordPress core, plugins and themes from trusted sources where appropriate.
  • Remove unauthorized users, files, plugins and scheduled tasks.
  • Rotate credentials and salts.
  • Review hosting, SSH/SFTP and control-panel accounts.
  • Review DNS and CDN settings.
  • Check redirects, admin accounts and content for unauthorized changes.
  • Confirm backups are clean and working.
  • Document what happened and what controls were added to prevent recurrence.

Authentication

ACCOUNT PROTECTION
18WP 2FA – Two-factor authentication for WordPressRecommended MFA knowledge resource

Why MFA?

A stolen password should not automatically provide access to an administrator account. MFA adds another verification factor.

Recommended plugin

WP 2FA – Two-factor authentication for WordPress by Melapress provides wizard-driven setup, authenticator-app TOTP, email codes, backup codes and policies for enforcing 2FA. The WordPress.org listing documents free 2FA support for users and additional premium features.

Implementation

  1. Plugins → Add New.
  2. Search for WP 2FA.
  3. Install and activate the plugin by Melapress.
  4. Configure an authenticator method and recovery codes.
  5. Require MFA for administrators and other privileged roles where appropriate.
Recovery: establish backup/recovery procedures before enforcing MFA on production accounts.
WP 2FA on WordPress.org →
19CAPTCHA / Bot ProtectionReduce automated abuse

Where?

Consider bot protection for login, registration, password reset, comments and public forms where automated abuse is a concern.

Use it as one layer

Combine bot protection with rate limiting, MFA, strong passwords and sensible account policies. CAPTCHA alone does not secure WordPress.

Developer tip: choose a solution compatible with your privacy, accessibility and plugin requirements, then test all authentication and form flows.

Security Headers

BROWSER PROTECTIONS
20Headers Security Advanced & HSTS WPYour requested WordPress plugin

What does it do?

The plugin adds HTTP security headers and HSTS. Its WordPress.org documentation covers CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Permissions-Policy.

Install and configure

  1. Plugins → Add New.
  2. Search for Headers Security Advanced & HSTS WP.
  3. Install and activate it.
  4. Open Settings → Headers Security Advanced & HSTS WP.
  5. Review existing headers from your host, CDN and other plugins to avoid duplicates.

Header examples

Strict-Transport-Security: max-age=31536000
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
HSTS caution: verify the entire domain and required subdomains work correctly over HTTPS before long HSTS durations or preload. CSP should be tailored to the actual site's resources rather than copied blindly.
Headers Security Advanced & HSTS WP →HSTS Preload Check →
21Know the Main Security HeadersUnderstand before configuring

HSTS

Strict-Transport-Security tells browsers to use HTTPS for future requests after a secure connection.

Content Security Policy

Content-Security-Policy controls which resources and behaviors browsers allow. Build it for the actual WordPress site because a restrictive generic policy can break plugins and third-party resources.

X-Content-Type-Options

nosniff reduces MIME-type sniffing behavior.

Referrer-Policy

Controls how much referrer information is sent with requests. strict-origin-when-cross-origin is a useful starting point for many sites.

Permissions-Policy

Controls access to selected browser capabilities. Only allow features the site actually needs.

Firewall & Security Plugins

LAYERED DEFENSE
22Wordfence / WAF / Brute-Force ProtectionConfigure a security layer

What should the security layer provide?

  • Web application firewall / malicious-request filtering
  • Brute-force and login attack protection
  • Rate limiting
  • Malware and file-change scanning
  • Known vulnerability detection
  • Security alerts

Implementation approach

  1. Install a reputable security plugin and keep it updated.
  2. Enable the firewall.
  3. Enable brute-force/rate-limit protections appropriate to traffic.
  4. Enable MFA for administrators.
  5. Configure useful alerts and scheduled scans.
  6. Test forms, login, APIs, caching and integrations after tightening rules.
Avoid stacking blindly: multiple plugins, CDNs, hosts and server rules can duplicate WAF, login and header controls.

Backups & Recovery

PREPARE FOR FAILURE
23Backups You Can Actually RestoreFiles + database + recovery

Back up

  • WordPress database
  • wp-content and required site files
  • Uploaded media
  • Important deployment/server configuration

Good practice

  1. Automate backups.
  2. Keep copies away from production.
  3. Use an appropriate retention policy.
  4. Protect backup access with strong credentials and MFA.
  5. Perform test restores periodically.
Key principle: a backup that has never been restored is an assumption, not a verified recovery plan.

26Penetration TestingAuthorized security assessment

What is it?

A penetration test combines automated and manual techniques to identify and validate security weaknesses.

Before testing

  • Get written authorization.
  • Define scope and targets.
  • Set testing windows and production-impact limits.
  • Have backups and rollback procedures ready.

Useful WordPress areas

  • Outdated core, plugins and themes
  • Authentication and MFA
  • User enumeration
  • Exposed backups/configuration
  • File uploads
  • REST API/custom endpoints
  • Access control
  • Headers and TLS
  • Logging and alerting
Reminder: do not run intrusive tests against third-party sites without permission.
